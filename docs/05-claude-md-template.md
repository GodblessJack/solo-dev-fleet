# 05 · CLAUDE.md 项目宪法怎么写

CLAUDE.md 是每个 Claude Code 会话启动时自动加载的「宪法」。在舰队里它承担四件事:**沟通规则、工程命令、硬性约束、流水线口径**。本仓 `templates/CLAUDE.md` 是可直接套用的模板,这里逐段讲设计意图。

## 5.1 沟通原则(置顶,最高优先级)

单人舰队最大的协作成本是「AI 说话人听不懂」。模板固化了四条:

1. 禁止高度概括后隐藏细节——不许抛抽象标签让用户做选择;
2. 提问和选项必须基于调查、还原事实——讲清流程现状、改后流程、来龙去脉;
3. 多方案对比逐方案展开——改哪些文件、体验变化、风险副作用,让用户能独立判断;
4. 完工汇报直观量化——改了哪几个文件、建了什么单(带链接)、推了哪个 commit(带 hash),禁行话包装。

## 5.2 工程命令 + 门禁

写明 build/test/lint 命令,并规定「提交前必须全过」——这是 CI 门禁的本地镜像,S2 提 PR 前自查,CI 不过是小概率事件。

## 5.3 硬性约束(按项目裁剪)

模板里的通用项:

- **remote 红线**:push 只推协作 remote,永不碰上游 fork 源(如果适用);
- **凭证纪律**:凭证只进 `.env.local`/keystore,绝不入库、不进 issue/PR 正文;
- **交付物零占位**:不许「模拟/原型/待定/占位」字样;
- **术语口径**:界面与文档文案遵守项目术语表(如果有 CONTEXT.md);
- **无由不导出/无由不烧资源**:昂贵的操作(渲染/真调 API)默认不执行,执行必验证结果。

## 5.4 Git 与 GitHub 工作流段

- main 只接受 PR 合入(squash);分支命名即路由(fix/feature/chore);
- 提交信息格式 `<type>: <说明> (#<issue号>)`;
- **机制层例外**:workflow/命令/CLAUDE.md/ADR 等机制类改动,AI 可不建 issue 直接改,但**落地一律走 PR**(chore/ 分支,正文说清动机),产品代码仍走完整 issue 门禁——这是「什么情况下不建 issue」的明文答案。

## 5.5 三道闸门段

设计闸门(拷问→ADR→拆单)/ 就绪闸门(三要素齐备才打 ready)/ 上下文闸门(实现起新会话,主会话不硬撑)。见 docs/04 §4.3。

## 5.6 流水线会话段

六个角色每个一段:谁、在哪跑(目录/端口/worktree)、认领什么、提单/打标纪律、红线。这段是 CLAUDE.md 与 `claude-commands/` 的**接口**——CLAUDE.md 写口径摘要,命令文件写完整剧本,两处冲突以命令文件为准(但应当同步改)。

## 5.7 写宪法的三条经验

1. **每条规则带「为什么」**:事故驱动的规则写明来源(哪次事故、什么根因),AI 对「有故事的规则」遵守度显著高于裸禁令;
2. **规则要可执行**:不写「注意质量」,写「build+test+lint 全绿才许提 PR」;
3. **越具体的纪律越靠前**:沟通原则置顶,因为它影响每一次交互;技术性约束放后面。
